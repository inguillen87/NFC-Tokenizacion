# Consumer verification and post-TAP benefits

This API increment starts from the published commit `daded91e5dd04be988ba5a541eee75d73ac02ab5`. It changes consumer challenge consumption, the existing TAP-dependent loyalty/trivia services and the isolated experience-event signer. Its paired WEB increment starts separately from `fc7502625bac1d4aba29db4261e9f9e6cec5a921` and changes only that event's server forwarding/signing and validation. The NFC cryptographic verifier, counters, durable TAP receipts, database migrations, ownership/PIN policy, points formulas and Dashboard source remain unchanged.

OTP and magic-link verification now lock and consume the same linked challenge group in one SQL statement before creating or updating a consumer or issuing a session. Only the winning verifier proceeds. All linked challenges must still be unused, unexpired and unlocked after the database locks have been acquired. A downstream account/session failure leaves the consumed challenge unavailable; requesting a new challenge is the recovery path. This is not a transaction that rolls back all account/identity writes after consumption.

TAP-dependent benefits require the exact current tag identity to belong to the event's tenant and batch and to remain active in both operational and lifecycle state. The writer holds a shared tag row lock while it commits, so a revocation committed first prevents the award/enrollment/redemption. A benefit that acquired its lock first completes before revocation can commit. Missing or ambiguous identity and unrecognized validation results grant no new benefit. Historical event reads remain available.

Authenticated electronic opening (`VALID_OPENED` and supported opening-history states) remains distinct from forgery or an administrative/manual opening. Configured consumption benefits remain possible for authentic opened packaging. Existing manual-opening, replay, cryptographic and administrative refusals remain in force. Saving a product in history does not certify an unopened package, complete a purchase, transfer ownership or grant points.

Blocked/deleted loyalty members cannot be reactivated by the member upsert, and TAP-dependent award writers preserve their refusal. Previously earned balances and workflows independent of a new TAP retain their existing contracts.

The focused PostgreSQL checks additionally reproduced existing bookkeeping failures: a data-modifying CTE tried to update the ledger or quiz-attempt row it had just inserted in the same statement. Corrected bookkeeping uses the insertion's `RETURNING` result and the locked member balance, preserves idempotency, and returns a receipt for a coherent completion. A concurrent conflicting quiz ledger reservation rolls back the whole statement, including the attempt, member update and membership projection. Zero-point completion remains supported. This increment does not repair historical production balances or infer that any particular customer was affected.

The two physical save requests observed on 2026-10-04 returned HTTP 200 for events 734 and 735 on the previously published API/WEB. Those logs alone do not certify durable rows, which event was electronically opened, physical package contents, or acceptance of this new candidate. No signed NFC URL or customer session was replayed for this work.

The contemporaneous experience-event investigation found the shared `PUBLIC_DEMO_SHARE_SECRET` configuration absent in WEB and API metadata. The previous source returns `share_token_unavailable` before forwarding when that key is absent. The historical log responses had no reason/body, so that explanation for the two observed 503 responses is an inference. The repair uses a dedicated server-only `PUBLIC_EXPERIENCE_SHARE_SECRET` and an explicit signature domain for experience-event only. The general demo signer remains disabled. Activity still requires a fresh TAP capability, a server-derived tenant/event context, allowed client event type, trust validation and durable idempotency. The dedicated signature grants no commercial rights and cannot serve another CTA or a public-certificate signer.

The configuration review also identified current-lifecycle limitations in other commercial workflows that this activity repair does not enable or fix. Current-state guards in this increment cover TAP-dependent loyalty/trivia; they are not a claim that every ownership/warranty/tokenization writer has been hardened. These limitations remain separately documented, and historical production records are not rewritten.

Local tests, real PostgreSQL tests with synthetic fixtures, CI, Preview, production publication and physical acceptance are separate evidence states. The final publication receipt records the exact commits, deployment identities, configuration operations and completed gates; this source document alone does not certify a deployment or a WhatsApp/Meta OTP delivery.
